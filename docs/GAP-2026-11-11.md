# 同类开源项目差距清单（2026-11-11 · v1.34.0）

调研方式：一个子智能体独立调研 11 个开源项目，我负责核实影响排序最大的 6 条代码结论、
抽查 1 条外部事实，然后重排。**分歧点写在第 5 节**，没有直接采信子智能体的排序。

数据口径：star / 贡献者 / 最近发版取自各项目 GitHub API 与官方文档，查询日期 2026-11-11。
我们的现状一律给 `文件:行` 或实测命令，不给"看起来没有"这种判断。

---

## 1. 先定位：它是什么，不是什么

它是一台**单机文档记忆 appliance**，不是缩小版 RAGFlow / Dify。

形态最像 Reor / Khoj（本地目录、文件即数据、个人使用），治理最像 RAGFlow（引用校验、
版本审批、评测门禁）。竞品分三条路走：平台型（Dify / AnythingLLM / Open WebUI）赢在
接入面与规模，PKM（Reor / Khoj / Logseq）赢在日常使用，记忆层（Mem0 / Letta）赢在时序与自更新。

**本项目唯一同时具备的组合**是：零依赖 + 引用可验证 + 知识库版本审批 + MCP 可写。
代价是生态位很窄——单用户、单机、中文、文本为主。一旦换成团队协作、扫描件、十万级语料，
短板会集中暴露。所以下面每一条差距都要问一句"这在我们这个定位里算不算缺陷"。

## 5. 我与子智能体排序的三处分歧

写出来是因为分歧本身比结论更有信息量。

**① 把 OpenAI 兼容从第 2 提到第 1。** 子智能体按"影响面"排，表格数值排第一。但按
`影响 × 概率 ÷ 成本`：接不上是**每个想集成的人第一步就撞上**（概率 4），且只要 2–3 人日；
表格只有在"上传带百分比或日期的 xlsx"时才触发（概率 3），要 3–5 人日。所以先做 A2。
**但**我把 A1 的影响面调到最高——数字错属于静默失败，金融场景下后果比接不上严重。

**② 表格那条的定性改了。** 子智能体标"能力缺失"，我改成"已知取舍导致的定位风险"。
依据是 `src/table_text.py:7-11` 明确写着代价，作者没有假装支持。这不改变它该修，
但改变了修法：不是补一个解析器那么简单，而是要么引 openpyxl（破坏零依赖），
要么自己解析 `styles.xml` 的格式索引。

> **已落地（v1.35.0）**：选了第二条，自己解 `styles.xml` 的 `numFmts` + `cellXfs`，
> 零依赖没破。百分比、日期、货币、千分位、负数括号、合并单元格都已生效，
> 端到端验证「稳盈90天的管理费率」答出 `3.50%` 而不是 `0.035`。

**③ 把 embedding 增量重建从第 11 提到 B1。** 子智能体按"用户会不会立刻发现"排，
它排在第 11。但它是**账单问题**：用付费 embedding 的用户，改一篇文档就付一次全库的钱。
而且修复路径清晰（按 chunk 增量），不该等到"规模上去"才做。

### A5 为什么不做

零依赖前提下没有可用的 OCR：Tesseract 要装二进制与语言包，PaddleOCR 要 torch + 模型权重，
两者都会把「解压即用」变成「先配环境」。现在的行为是**识别得出来 + 说清楚 + 给补救步骤**
（`need_ocr: true`，提示用手机扫描 App 或 Acrobat 转文字后另存）。这比假装能读要诚实，
也是本项目与 RAGFlow / QAnything 最实质的差距——承认它，而不是用规则版「伪 OCR」掩盖。

### B1 为什么原判断有误

原报告写「改一篇文档要全量重嵌，改 1 篇 = 全库账单」。核对代码后发现 `EmbeddingCache`
本来就按 `sha256(model|dim|text)` 缓存，`build()` 先查缓存再嵌缺失项。实测：100 块语料改 1 块，
只有 1 块走 provider。

真正的问题在别处，已修：

1. **缓存无上限**：每改一次条款就留一份旧向量，永远不会再命中，几个月后是几百 MB 死数据。
   现在按条数封顶（`EMBEDDING_CACHE_MAX`，默认 20000），命中即移到队尾，按 LRU 淘汰。
2. **成本不可见**：重建后只报 `embedded`，用户看到 0 会以为没生效。
   现在同时报 `reused` 与 `cache` 规模。

教训：差距清单里的性能结论必须落到「跑一次」上。这条如果照着改，会去重写一个本来正确的缓存层。
