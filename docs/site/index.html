记忆文档 · 可接入智能体的文档记忆应用

一句话定位：它是一份由你掌控、能被不同智能体读写的文档记忆。

把制度、手册、产品说明或任意文档变成可追溯的问答：只依据资料作答，逐条标注出处； 资料不足时明确说不知道，并给出相似问题。值得留下的回答存成结构化笔记， 会话记录也一并落盘——都在你自己选的存储区里，全是普通文件。

  • 数据不在浏览器里：笔记是 Markdown，会话是 JSON，~/记忆文档/ 整个目录拷走就是完整备份；
  • 接入方式以智能体为主：任意 MCP 客户端或 HTTP 调用 POST /api/notes 就能整理并写入；
  • 文件可自由修改：页面里能改原文（带版本冲突保护），也能交给系统里顺手的编辑器。

不接模型 Key 也能跑：自动进入离线抽取模式，检索、引用、评测全链路仍然可复现。

0. 定位：这是「文档问答 + 笔记」，不是只服务金融

同一个引擎可以挂任意文档，金融只是当前这套知识库的第一个实例：

  • 换知识库：把文档放进 data/knowledge/，或直接在知识库页上传（支持 .md / .txt / .pdf / .docx / .xlsx / .csv / .tsv，可一次多选，上传后立即重建索引）；
  • 换领域：设 APP_PROFILE=generic 即可去掉金融专属护栏（荐股拒绝），只保留注入、越权、隐私这些通用安全规则；
  • 换检索策略：RETRIEVAL=vector|bm25|hybrid（默认向量召回 + 重排），QUERY_EXPANSION=off|auto|llm。

为什么默认还是金融 profile：当前语料就是制度与产品说明，金融合规红线（不荐股、不替产品做收益承诺）在这套语料上是必要约束；换成你自己的文档时切 generic 即可。

补充说明「收益承诺」到底拦什么：问「这个产品保本吗」「年化多少」时不拒答，而是引用制度里「不得承诺保本保收益」「业绩比较基准不代表实际收益」的条款——这才是制度库该给的答案。真正被拒的是让助手替产品背书（必涨/稳赚/包赚/翻倍）和荐股。

0.1 先说清楚：这是工作流，不是 Agent

一句话区分：RAG 解决「知道」，Agent 解决「去做」。

本作品的本质是「检索 → 生成 → 引用」的固定链路（Prompt Chaining），分支可穷举，不需要上自主 Agent。判定标准很简单：能写出 if/else 穷举分支，就别用 Agent——上 Agent 只会引入不确定性、成本和运维负担。

什么时候才升级为 Agent：当需要模型动态决定调用哪些外部工具（查实时利率 API、算 IRR、提交工单、转人工），且走向依赖中间结果、分支无法穷举时。届时按「Chaining + 有界工具调用循环」升级，并强制 max_steps / 预算 / 停止条件 / 人工接管点 四件套。

  IDX[(索引 manifest<br/>model · dim · fingerprint)] -.-> RET
  RET -->|无命中| R2[no_answer + 相似问题]

  GEN -->|有 API Key| LLM[LLM 生成 OpenAI 兼容]
  GEN -->|无 Key / 调用失败 / 超预算| EXT[抽取式降级]
  LLM --> CITE[引用校验 [n] 对齐命中块]
  EXT --> CITE
  CITE --> LOG[(trace.jsonl 观测)]
  CITE --> OUT

3. 快速开始（零依赖，Python 3.11+）

方式 A：下载应用包

  1. 打开 Releases，下载 jiyi-app-<版本>.zip（同页附 SHA256SUMS.txt）；
  2. 解压到任意目录（路径尽量不含空格）；

默认只绑定 127.0.0.1。「绑本机」不等于安全：浏览器里的任意页面都能向 127.0.0.1 发请求， 且对端 IP 就是本机。所以 v1.19.1 起写操作必须通过来源校验（src/security.py）， 不能只靠 IP 判断「是不是自己人」。要在局域网访问，务必同时设置 ALLOWED_HOSTS 与 API_KEYS。

  • 文档结构建议用 Markdown 标题分节：切分器按标题/条款切块，结构越清楚，召回越准。

4.3 PDF / DOCX 接入（上传即用，运行时仍零依赖）

不需要你手动转换：在知识库页上传后，服务端按扩展名分派解析器，转成 Markdown 再入库。

4.6 真 embedding 与向量索引（可选，接口已隔离）

默认仍是零依赖的字符 n-gram 向量，保证 git clone 后不装任何东西就能跑。 配置 embedding 后，RETRIEVAL=embedding 走真语义召回。

选型：为什么是「OpenAI 兼容协议 + FAISS」

决策选择理由
模型协议OpenAI 兼容 POST {base}/embeddingsbge 用 TEI / Xinference / vLLM / Ollama 部署后都暴露同一路径；换模型只改环境变量，不改代码
模型bge（中文优先）或 OpenAI embedding中文制度/产品说明里「起购 vs 起点」这类同义改写，字符 n-gram 补不上，真 embedding 才能补
向量库FAISS（默认 IndexFlatIP）语料是 10²~10⁵ 量级的内部文档，单进程只读、按版本整体重建；flat 是精确检索，持久化只有两个文件，不引入服务端
不选 Chroma—需要 collection/元数据过滤/多租户时才划算；它会带 sqlite/duckdb 等一串传递依赖，与本项目「小依赖、可离线」冲突。接口已隔离，将来加 ChromaStore 不影响检索层
加速器NumPy / FAISS 均为可选没装时自动退到纯 Python 精确内积；31 个块 × 1024 维的查询开销可忽略

维度与索引配置

维度不写死：首次构建时探测模型实际维度并写进 manifest.json；配置了 EMBEDDING_DIM 就做一致性校验，不一致直接报错（不截断、不补零）。这样换 bge 版本（512/768/1024）不会静默错配。

EMBEDDING_PROVIDER=openai          # none | openai | bge（bge 走同一协议）
EMBEDDING_BASE_URL=http://127.0.0.1:8080/v1
EMBEDDING_MODEL=BAAI/bge-m3
EMBEDDING_DIM=0                    # 0=自动探测；已知维度时填上可提前校验
EMBEDDING_BATCH=16
EMBEDDING_TIMEOUT_S=8
EMBEDDING_MAX_RETRIES=2
EMBEDDING_BUILD_BUDGET_S=600        # 建库预算，与单次查询的 30s 分开
EMBEDDING_INDEX_DIR=data/index
VECTOR_STORE=auto                  # auto | pure | numpy | faiss | faiss-ivf
VECTOR_IVF_NLIST=64
VECTOR_IVF_NPROBE=8
RETRIEVAL=embedding

规模上限（实测，本机 Python 3.13）：没有 numpy/faiss 时走纯 Python 点积， 5000 块 × 1024 维约 186 ms/查询，20k 块约 750 ms，而且 GIL 下并发会线性变差。 默认的 hash 向量路径（RETRIEVAL=vector）5000 块只要约 18 ms，不受这个限制影响。 所以：纯后端建议 ≤2k 块；再大就装 numpy/faiss，或把 EMBEDDING 换成本机模型端点 + VECTOR_STORE=faiss。这不是「慢一点」，是单次问答里多出半秒以上的等待。

索引文件（data/index/<model>/）：

文件内容
manifest.json模型、维度、度量（cosine）、语料指纹、后端、块数、构建用量
vectors.jsonlL2 归一化后的向量；换后端不必重新 embedding
index.faissFAISS 索引（可选，加载更快）
embeddings.cache.jsonl按 `modeldimtext` 哈希缓存，知识库小改只重算变化块

索引策略：

  • 指纹失效：manifest 的 fingerprint 覆盖「模型 + 每块 id/正文哈希」，知识库或模型一变就自动重建；
  • flat vs IVF：faiss-ivf 只在 N ≥ nlist × 30 时启用，否则训练样本不足会退化/报错，自动回退 flat 并在 manifest 记明；
  • nlist/nprobe：经验值 nlist ≈ 4√N，nprobe 从 8 起调；本演示 31 块用 flat，不引入训练误差；
  • 查询缓存：同一问题 128 条 LRU，评测重跑/多轮追问不重复计费。

迁移步骤（可回滚）

  1. 起一个 OpenAI 兼容的 embedding 端点（TEI / Xinference / Ollama 均可），确认 curl {base}/embeddings 返回向量；
  2. 设置上面的环境变量，先 不要 改 RETRIEVAL；
  3. python tools/build_index.py --rebuild --check "大额存单可以转让吗"，确认 dim、backend、抽查命中；
  4. 跑 python tests/eval_retrieval.py 对比 R@1 / MRR，有增益再切；
  5. 改 RETRIEVAL=embedding 并重启；观察 /api/health 的 retrieval_detail.index_status；
  6. 回滚：把 RETRIEVAL 改回 vector 或 bm25，无需删索引；索引坏了下一次启动会自动重建。

未配置模型、服务不可达、超时、维度不一致时：查询当次回退词法检索，答案标 degraded，/api/health 暴露 fallback_error；不会让服务起不来，也不会静默返回空结果。

4.8 知识库版本、审批与文档级回滚

data/kb/ 是运行时版本库（已加入 .gitignore），data/knowledge/ 只作为首次初始化的种子：

data/kb/
├─ state.json                 # {"active":"v0003","next_version":4,...}
├─ versions/v0001/
│  ├─ manifest.json           # 作者、来源、每份文档 sha256
│  └─ files/*.md
├─ versions/v0002/...
├─ pending/chg_0001/          # 待审批：request.json + 暂存文件
│  └─ request.json
└─ changes/chg_0001.json      # 已审批/已拒绝的历史（只增不改）

三条不变量：

  1. 版本只增不改：回滚不是把指针拨回去，而是用旧内容生成新版本，历史可追溯（谁、何时、从哪个版本恢复）；
  2. 激活原子：版本目录写完后才 os.replace 更新 state.json，读侧不会看到半成品；
  3. 按文档回滚：只替换目标文件，其余文档保持当前版本，避免「为回滚一份文档把别人刚发布的也退回去」。
KB_STORE=on
KB_DIR=data/kb
KB_SEED_DIR=data/knowledge
KB_APPROVAL=auto        # auto=本机管理员直通，其他来源走审批 | on=全部审批 | off=全部直通

审批流（KB_APPROVAL=on 时）：

# 1) 上传 -> 生成待审批变更，不进检索
curl -s -X POST localhost:8000/api/knowledge/upload \
  -H 'Content-Type: application/json' \
  -d '{"name":"04_采购制度.md","content":"# 采购制度\n\n## 一、审批\n\n采购合同由财务负责人签字。\n"}'
# -> {"ok":true,"pending":true,"change_id":"chg_0001","version":"v0001"}

# 2) 管理员审批 -> 生成 v0002 并重建索引

  -H "X-Admin-Token: $ADMIN_TOKEN" -H 'Content-Type: application/json' \

# 3) 按文档回滚到 v0001（只回滚这一份）

  -H "X-Admin-Token: $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"04_采购制度.md","to_version":"v0001"}'

4.9 关键词直出：命中条目就本地返回，不调用模型

这条路径解决的是「问题根本不需要模型」的情况：用户上传的是清单、档案、标签类文档， 答案就是原文里的某一行，走检索 + 生成只会更慢、更贵，还可能被改写。

场景：小a 上传 小a的生活习惯.md，里面有爱吃/不吃/忌口/作息/爱好/宠物。 系统抽出 42 个条目；问「我不吃香菜」命中「香菜」，直接返回原文那一行与出处， 0 次 API 调用；问「今天天气怎么样」不命中，回退到正常检索。

Q: 我不吃香菜
路径=本地关键词 · 模式=keyword_local · 调用API=否 · 0.1 ms
· 不吃的食物：香菜、动物内脏、苦瓜
出处: [1] 小a的生活习惯·一、饮食偏好

抽什么、什么时候直出

来源例子直出
清单项- 爱吃的食物：火锅、寿司、拿铁✓ 每项 + 标签都可命中
表格行表头「起购金额」、单元格「1 元」✓ 标签作为条目
标签值起床时间：早上 7:30✓
## 关键词 段逗号/顿号分隔的词✓ 权重最高
章节标题## 三、个人爱好✗ 只用于展示与召回提示
普通句子「风险等级越高，波动越大」✗ 只走检索

只认精确包含（词或同义词），不做模糊近似：关键词直出的错误代价比「多走一次 RAG」高得多。 因此制度类文档的常规问题不会被截胡——test_keywords.py 里有专门的回归用例守着这条线。 个人偏好类条目的核心词（「喜欢的音乐」→「音乐」）只在第一人称提问时生效， 「明天天气」不会因为文档里有「讨厌的天气」被截胡。

命中之后的四道闸门

命中不等于直出。下面四道闸门（KEYWORD_GUARD=on，可关掉做 A/B）在 v1.5.0 加入， 对应的是实测翻车现场，不是纸面规则：

闸门触发例子处理记录
否定作用域「我不爱吃香菜」里的「爱吃」该次出现不算命中negated

被挡下的词写入响应的 keyword_rejected，并计入 rag_keyword_rejected_total{reason} 与 rag_keyword_gate_total{gate}—— 规则是在救火还是误伤，看指标，不靠感觉。

tests/eval_keyword.py 是这套规则的标尺：13 条应直出用例全部命中，9 条不应直出用例 0 误伤， 其中 2 条被解释型闸门主动挡下（而不是碰巧不命中）。

接了 API 之后：只增强，不替换

每份文档在上传/重建时做一次模型整理：

  • 生成 ≤60 字摘要，展示在知识库关键词面板；
  • 生成 6~16 个关键词与同义说法（「咖啡」→「拿铁」、「芫荽」→「香菜」），补词面差异；
  • term 必须在原文出现，snippet 一律从原文截取，模型不提供答案句子；
  • 解析失败 / 超时 / 429：保留本地条目，失败原因写 /api/health.keywords.error，不影响上传；
  • 按文档内容 hash 缓存，语料没变不重复调用；KEYWORD_LLM=off 可完全关掉。

  • 同义词只解决词面差异，不解决跨段推理；需要比较、计算、归纳的问题仍走 RAG。
  • 清单里的单字项（如「辣」）只在白名单内接受，避免「的/了」这类字误触发。
  • 否定只处理命中位置前 3 个字的简单否定；双重否定、反问、跨句否定仍可能判错，

  • 关键词索引按文档 hash 全量重算条目（本地抽取很便宜）；模型整理只对新增/变更文档调用一次。
  • 没有 API Key 时只有本地条目，没有摘要和同义词；这是可用性差异，不是静默降级。

4.10 流式、多轮与引用原文（v1.6.0）

流式输出

问答页默认请求 POST /api/ask/stream，服务端以 SSE 推送：

事件含义前端动作
delta生成中的文本增量追加到答案区
replace上游中断，整段降级为抽取式替换已渲染的文本
final完整结果（含引用、校验后的答案）用正式答案卡替换，绑定反馈与引用

生成中发送按钮变为「停止」，AbortController 中断请求；服务端写失败即停止。 流式不重试半截答案：上游在 [DONE] 前断开会被识别为截断，整体降级并让前端替换。

多轮会话

session_id 由前端生成并存 sessionStorage，服务端只保留最近 3 轮（30 分钟过期、最多 1000 个会话）。 只有指代/省略式追问（「那 R2 呢」「还有呢」）才把上一轮问题拼进检索问题，独立问题不拼， 避免「R2 需要双录吗」被上一轮带偏。context_query 会写进响应与 trace，可复核。

边界：会话存在单实例内存里；多实例部署需要把它换到 Redis，否则负载均衡后追问可能落到另一台。

引用原文

每条 citation 带 doc_id、chunk_index、version、snippet。问答页的 [n] 是可点击按钮， 调用 /api/source 打开右侧原文抽屉，展示完整知识块并高亮命中行；不做文件路径拼接， 只接受当前索引里真实存在的块，越界返回 404。

审批界面

知识库页顶部展示待审批变更（作者、文件动作、风险提示），「查看 diff」调用 /api/kb/change 展示统一 diff；「通过 / 驳回」直接调用审批接口。每份文档新增「历史」， 可查看版本列表并回滚。配置 ADMIN_TOKEN 时，审批面板会出现令牌输入框（存 sessionStorage）。

未命中

不再提交工单：统一返回「无法找到答案。」，同时保留相似问题。/api/handoff 与工单表单已删除。

4.11 传输、日志与表格入库（v1.7.0）

HTTP 传输层

项之前现在
协议HTTP/1.0，每请求新建连接HTTP/1.1 + 定长响应，连接可复用
压缩无，/ask 整页 51 KBgzip，51 KB → 15.5 KB（省 70%）

实现在 Handler._send 一个出口里完成：任何路由都不会漏压缩、漏 Content-Length。 gzip 只压 text/* 与 application/json，小于 512 字节不压（省下的还不够压缩头）。 ETag 取内容 sha256 前 20 位并标 W/，这样同一内容在压缩/未压缩两种表示下命中同一个校验值。

没做：把内联 CSS/JS 抽成带 hash 的独立静态资源。当前方案已拿到主要收益（首屏 -70%、重复访问 0 字节）， 拆资源要改页面骨架与构建流程，收益递减，留到后面按需再做。

日志轮转与尾读

logs/*.jsonl 改成「写时轮转 + 读时尾读」：

  • 单文件超过 LOG_MAX_BYTES（默认 16 MB）转成 .1，最老的 .3 删除，LOG_KEEP 控制份数；
  • /api/metrics、/api/audit、/api/trace 从文件尾部按 64 KB 反向读取，凑够行数即停。

实测 37 MB trace：summarize(1000) 11 ms，全量读取 86 ms；文件越大差距越大，且内存占用不再随运行时长增长。

判域前置、扩展后置

查询扩展要付一次 LLM + 一次 embedding。旧顺序是「先扩展、再判域」，域外问题也要付这笔钱。 现在先用原问题检索并过闸门，通过之后才扩展；扩展结果只在分数更高时替换原结果。 域外问题因此少 1 次 LLM + 1 次 embedding。扩展调用本身失败会降级为原问题检索 （expansion_error 写入 trace），不再让整个问答 500。

答案元信息与未命中反馈

答案脚注显示：知识库版本、引用条数、引用覆盖率、检索分，以及原有的通道/模型、模式、耗时、降级原因。 未命中显示「最高分 / 阈值」，让人知道差多远，而不是只给一句「无法找到答案」。

未命中的反馈从「有用 / 没用」改成「应该怎么答 + 哪份文档有答案」，字段写入 logs/feedback.jsonl （expected / document / behavior / query / kb_version），可直接转评测用例或补文档。

会话历史与导出

对话存 localStorage（最近 40 轮，单条答案截断 6000 字），刷新后恢复最近 12 轮； 「导出 Markdown」把问题、答案、引用与元信息写成可归档的 .md。清空对话会同时清掉本地记录。 这是「回看 / 导出」的历史，与服务端 3 轮上下文（用于追问改写）是两件事，互不替代。

表格入库（xlsx / csv / tsv）

  • xlsx 用标准库解 zip + XML（sharedStrings + worksheet），不引第三方库；
  • 每个工作表转成一个 Markdown 表格，按整行入库：直出答案是 产品名称：稳盈 Plus 30 天 · 起购金额：1000 元 · 风险等级：R2，不会把管道符原样吐出来；表头也能命中（问「起购金额」给第一行数据）；
  • csv/tsv 先试 UTF-8，再退 GB18030（Excel 导出的中文 CSV 多是 GBK）；
  • 单元格里的 | 会转义，不会撑坏表结构；只有表头没有数据行的工作表跳过并提示。

边界：不解析样式，日期显示为序列号、合并单元格只在左上角有值。需要保留格式就另存为 CSV。 扫描件 PDF 的提示改为可操作步骤（先 OCR、另存为 docx/txt 再上传），响应带 need_ocr。

4.12 后台重建、深色模式与开放接口（v1.8.0）

后台 + 增量重建索引

上传 / 删除 / 审批通过后，接口只等版本落盘就返回，索引在后台线程里构建：

POST /api/knowledge/upload  → 约 100ms 返回 {rebuilding:true, chunks:null}
                              后台：解析变更文件 → 重建检索器/关键词 → 原子替换
GET  /api/health            → index.rebuilding=false, last_ms, parsed_docs, reused_docs
  • 重建期间继续服务：旧索引不会被清空，问答照常；代价是新文档有短暂的「已入库但还搜不到」窗口（本机 31 块约 15 ms，600 文档按 embedding 耗时而定）。
  • 只重读变更文件：load_corpus 用文件 mtime+size 做签名，未变的文档复用上次分块；实测改一份文档时「解析 1 / 复用 3」。
  • 连续触发合并：重建中再次上传只置 pending，同一个线程跑完当前轮再跑一轮，不并发重建、不为每次上传起线程。
  • 失败可见：构建异常写入 index.last_error，旧索引继续服务；知识库页轮询到失败会提示，不静默。

汇报页缓存与版本硬链接

4.13 智能体笔记：对话 → 个人笔记（v1.10 起，v1.12 补齐四条通道）

目标：让任意智能体把对话里值得留下的那几段整理成一篇结构化笔记，落到你自己的目录， 人能离线看改，下一个智能体直接读同一份文件——内容在智能体之间流动，靠的是文件而不是某个平台。

存储结构（文件是唯一真相）

NOTE_HOME（默认 ~/agent-notes，可用环境变量或 --home 覆盖）
├─ notes/2026/10/20261024-205142-5fc510.md   # 一篇笔记 = 一个文件，路径即时间线
├─ assets/<id>/                              # 附件（大代码块等）
├─ index/notes.jsonl                         # 派生索引，删了会自动重建
├─ exports/                                  # 导出的单文件（HTML / JSON）
├─ .trash/                                   # 软删除，可找回
└─ AGENTS.md                                 # 给智能体读的接入说明（首次初始化自动写入）

## 摘要
根据办法第十二条，退税率按出口货物适用税率执行，2026-11-01 起统一按 13% 执行；决定由财务部在每月 5 日前复核。

三个设计点：

  • 索引只是缓存：index/notes.jsonl 删掉、改坏、被人清空都不丢数据；notes list 会扫盘重建，条数以磁盘 .md 为准。
  • 手改优先：你用任意编辑器改标题、加小节、删段落，下次读就是新内容（按 mtime+size 自动刷新索引）；front matter 写坏也不会报错，会降级成 external: true 继续能读。
  • 重复内容不重复落盘：hash 是选中内容的指纹，同一段对话再存一次返回 duplicate_of，不生成第二个文件。

命令行（任何只能执行命令的智能体都能用）

export PYTHONPATH=$PWD

# 预览（不写盘）：先看整理成什么样

# 保存，只存第 2-4 条消息

  --kind decision --tags 税务,出口退税

# 查询
python -m src.notes list --tag 税务 --since 2026-10-01 --limit 20

python -m src.notes stats                    # 数量与标签分布
python -m src.notes rebuild                  # 索引丢了/外部文件多时重建

conv.json 就是一段对话：

{
  "messages": [
    {"role": "user", "text": "出口退税的退税率按什么标准执行？"},
    {"role": "assistant", "text": "根据办法第十二条…决定由财务部在每月 5 日前复核。"}
  ],
  "select": {"mode": "all"},
  "hint": {"title": "出口退税申报口径确认", "kind": "decision", "tags": ["税务"]},
  "source": {"agent": "claude-desktop", "session": "sess_1"}
}

select.mode 支持 all / indices（下标数组，从 1 开始）/ range（start、end）/ keyword， 另有 max_chars 限制单次入库长度（默认 20000 字，超出会截断并在响应里标 truncated）。

摘要：默认不联网，模型只是增强

digest: rule 是默认引擎：分句、按数字/结论词/位置打分、归类到摘要/要点/决策/待办/引用， 不联网、不花钱、永不抛异常。没有 Key 也能完整跑通保存 → 读取 → 再被其他智能体读取。

要用模型就加 --digest auto（有 Key 就用，失败回落）或 --digest llm（必须成功）。三条约束：

约束实现
输出必须合法只认固定 JSON，剥 ``json 围栏；摘要` 为空、字段类型不对都算无效
永不因模型失败而丢内容auto 模式下超时/限流/坏 JSON 一律回落规则摘要，保存照常成功
回落必须留痕front matter 记 digest: rule + `digest_fallback: timeout \invalid_output \network \no_key`

模型给的小节名不在标准集里会被丢弃（不把奇怪结构写进文件）；kind 非法回落 qa， 缺标题用 hint 补。--digest llm 失败时抛可读错误并提示改用 --digest rule，不静默降级。

笔记检索：词面 + 语义两档（v1.25）

SSE（v1.24）：请求头带 Accept: text/event-stream 时按 Streamable HTTP 回一条 event: message 帧再关流——严格的客户端只认这一种；不带则仍回普通 JSON。 GET /mcp 同样接受 text/event-stream，开一条只发 : ping 注释帧的下行流： 本服务没有「服务端主动发起的请求」，所以不推送任何伪造消息，这条流只用于 规范要求的连接与保活。两条路径都有硬上限（SSE_MAX_SECONDS 到点关闭、 MCP_SSE_MAX_CONN 默认 4 条并发，超了回 429）——长连接占的是请求线程， 不设上限几条挂死的流就能把服务拖到不响应。不带 Accept 的裸 GET /mcp 仍回 405。

4.16 接入 Dify：把本项目注册成「外部知识库」（v1.32.0）

Dify 里的 Agent 需要一个知识源。两种接法，这里只做第一种，原因如下。

接法做法结论
外部知识库Dify 调本服务的 /dify/retrieval 拿片段，自己生成答案推荐。职责清晰：本项目管检索，Dify 管编排与生成
自定义工具把 /api/ask 包成 OpenAPI 工具让 Agent 调不推荐。一次提问烧两次模型；citations 全文塞进 Agent 上下文；本项目的拒答语义与 Agent 的「自己答」互相打架
C3 的判断：这里不需要在本项目里加 Agent。Dify 那边已经是 Agent 了， 本项目再加一层循环只会变成「Agent 套 Agent」，两边都不知道最终由谁负责停。 本项目要做的是把「检索」这件事做成一个稳定的原子能力。

服务端已经做好什么

POST /dify/retrieval，实现 Dify 官方 External Knowledge API：

curl -X POST http://127.0.0.1:8000/dify/retrieval \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <API_KEYS 里的任意一个>' \
  -d '{"knowledge_id":"finance","query":"稳盈 Plus 的起购金额",
       "retrieval_setting":{"top_k":3,"score_threshold":0.5}}'
{"records": [
  {"content": "01_理财产品要素说明 · 一、「稳盈」系列产品\n「稳盈」系列…起购金额为 1 元…",
   "score": 0.795, "title": "01_理财产品要素说明",
   "metadata": {"doc": "01_理财产品要素说明", "section": "一、「稳盈」系列产品", "chunk": 0}}
]}

几个刻意的取舍：

  • 只检索，不生成。外部知识库的语义就是「给 Dify 提供上下文」。这里再调一次模型，

    • 等于一次提问付两次钱，而且两段答案会互相打架。

  • content 首行带「文档 · 小节」。Dify 只把 content 交给模型，不传 title；

    • 没有这一行，模型写得出答案却说不出来源，本项目「引用可核」的主张直接失效。

  • score 用本项目自己的归一化分（0–1），与 Dify 的 score_threshold 同一量纲，

    • 面板上调 0.5 就是真的 0.5。

  • 没命中返回 {"records": []}，不返回错误。Dify 的约定是「检索不到不算错」，

    • 回 404/500 会让整个应用报错。

  • metadata 一定是对象，不会是 null。Dify 明确说 null 会让它的检索流水线报错。
  • 不区分 knowledge_id：本服务只有一个语料库，填什么都接受。多库需求要改检索器

    • 支持按文档过滤，不是加个 if 能解决的。

在 Dify 里怎么配（三步）

前提：本项目服务在跑，端口 8000。

  1. 注册 API 连接：知识库 → 右上角「外部知识库 API」→ 添加
  • 名称：本地金融问答
  • API 接口地址：http://host.docker.internal:8000/dify（不要自己加 /retrieval，Dify 会追加）
  • API Key：配了 API_KEYS 就填其中一个；没配就随便填（服务端不校验）
  • 保存时 Dify 会打一次测试请求，成功才算通
  1. 创建外部知识库：知识库 → 连接外部知识库
  • 外部知识库 API：选上一步那个
  • 外部知识库 ID：finance（任意，仅回显）
  • Top K 填 3–5；分数阈值建议开，取 0.5（本项目的检索分实测：正常命中 0.6–0.95，

    • 误答区间 0.64–0.78，所以阈值卡太低等于没卡）

  1. 建 Agent 应用：创建应用 → Agent → 关联这个知识库 → 选模型 → 写提示词

排障：连不上先看这三处

现象原因处理
报「连接失败」，本服务日志没有任何请求Dify 的出站被 Squid 拦了（默认拒绝一切私有网段）见下一节
返回 403 host_not_allowed请求的 Host 不在白名单v1.32.0 起 host.docker.internal 已算本机别名，不用再配 ALLOWED_HOSTS
返回 401配了 API_KEYS 但 Dify 里填的 Key 不对两边改成同一个值

Dify 的 SSRF 代理放行（官方扩展点，不改默认配置）：

# Dify 的 docker 目录下，新建 envs/infrastructure/ssrf-proxy.env
SSRF_PROXY_ALLOW_PRIVATE_DOMAINS=host.docker.internal
# 然后重建代理容器
docker compose up -d ssrf_proxy
# 验证：应看到生成的白名单里出现 host.docker.internal
# Git Bash 必须带 MSYS_NO_PATHCONV=1，否则 /etc/... 会被改写成 Windows 路径
MSYS_NO_PATHCONV=1 docker exec docker-ssrf_proxy-1 cat /etc/squid/dify_allow_private.conf

只放行这一个域名，不要去设 SSRF_PROXY_ALLOW_PRIVATE_IPS——那是按网段放行， 等于把整个私有网段对 Dify 的插件与工具敞开。

在 Dify 里搭智能体的完整配置（应用类型怎么选、提示词全文、模型参数、7 条验收用例、 以及这套方案比本项目原生弱在哪），见 docs/DIFY-AGENT.md。

OpenAI 兼容端点

任何 OpenAI SDK / LiteLLM / LangChain 只要把 base_url 指过来就能用：

# 模型清单（SDK 启动时会先探这个）

# 非流式

  -H 'Content-Type: application/json' \
  -d '{"model":"jiyi","messages":[{"role":"user","content":"稳盈系列起购金额是多少"}]}'

# 流式（SSE，以 data: [DONE] 结束）
curl -N http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"jiyi","stream":true,"messages":[{"role":"user","content":"稳盈系列起购金额是多少"}]}'

).choices[0].message.content)

三个刻意的取舍：

  • 只取 messages 里最后一条 user 当检索问题。把整段历史拼进去会让向量偏离当前问题

    • （追问场景实测 top-1 会掉到上一轮主题）；多轮上下文由 session_id 负责。

  • 引用放在非标准字段 citations，不拼进正文。正文里的 [n] 编号保留，方便直接展示；

    • 拼上一段「参考：…」会让客户端拿到的答案变成两截。

  • 不支持 tools / function_call / n>1，直接回 400 并说明原因。接了工具调用就变成 Agent，

    • 与「只依据资料作答、逐条标注出处」的定位冲突。

错误体是 OpenAI 形状（{error:{message,type,code}}）。这一点必须照做：SDK 只读 error.message，回本项目的 {ok:false,...} 时它只会显示「unexpected response」。

页码级引用

PDF 入库时按页写入 <!--page:N--> 标记，切分时换算成 Chunk.page 并与 chunk.text 分开存 （标记不进正文，否则会被当成人话检索）。于是引用能显示「第 12 页」，/api/source 也会返回页码。

curl -s "http://127.0.0.1:8000/api/source?doc=演示制度_销售适当性管理实施细则&chunk=3" | head -c 300
# {"doc_id":...,"section":"...","page":7,...}

为什么把标记写进 Markdown 而不是另存一份页码映射：切分发生在「以后某次重建」， 那时手里只有文件。一个注释行是自描述的，映射表还要防它和文件不同步。

检索调试台 /debug

答错时最费时间的判断是「没检索到」还是「检索到了被阈值挡住」。这一页把候选、分数、 是否被 MIN_SCORE 挡掉（kept: false）一次摊开，等同于别家的 Retrieval Testing：

POST /api/search/debug  {"query":"稳盈系列起付金额","top_k":4}
→ {min_score, recalled(=top_k×3), kept, candidates:[{score, kept, section, page, text}]}

页面在左侧栏「调试」，或直接访问 /debug。

更多入库格式：PPTX / HTML / EML

零依赖自己解（zip+XML / html.parser / email）：

  • PPTX：按页生成 ## 第 N 页 章节；空页保留占位（否则后面页码整体前移，引用指错页）。
  • HTML：保留标题/列表/表格，丢掉 script/style/nav/footer——侧栏页脚每页重复，

    • 收进知识库只会变成高频噪声。

  • EML：主题/发件人/日期 + 正文（优先 text/plain，没有则转 HTML）；附件只计数不解析。

.doc / .xls / .msg 老格式仍需先另存；图片与扫描件要 OCR（仍未内置）。

python tests/eval_run.py --out tests/baseline.json        # 更新基线
python tests/eval_run.py --sleep 2 --out tests/report_llm.json   # 接模型跑一轮

  • 门禁：对抗用例 100% 通过（一条失败即非零退出，阻断发布）+ 总通过率 ≥ 90%
  • 仓库存留的报告：离线 26/26 = 100%（tests/baseline.json）、接入模型 26/26 = 100%（tests/report_llm.json，由评测者自备模型跑出）。这两份生成于拒答基线并入默认集之前，所以汇报页会把它们标成「旧」并提示重跑——页面不藏这件事
  • L1 断言只锁「行为 / 事实 / 安全」，不绑死措辞（如风险等级接受「R1 / R5 / 五档 / 五级」任一）；语义质量交给 L3。

5.1 L3 语义评分（LLM-as-Judge）

L1 判不了三件事：编造（关键词命中但数字是编的）、答非所问、多问只答一半。所以加一层裁判：

# 前提：先用当前版 eval_run 重跑 L1（报告需含 answer/context 字段）
python tests/eval_run.py --sleep 2 --out tests/report_llm.json
python tests/eval_l3.py --report tests/report_llm.json --sleep 1.5
python tests/eval_l3.py --report tests/report_llm.json --limit 8 --json   # 抽样快跑
  • 答案类用例按「忠实度 / 相关性 / 完整性」各 1–5 分；拒答类用例用合规 rubric（该不该拒、有没有泄露）。
  • 裁判只看【检索资料】+【回答】，禁止用自身知识补依据，避免“裁判比模型还懂”的假高分。
  • 门禁：忠实度均分 ≥ 4.0、无 faithfulness ≤ 2 的疑似编造、语义通过率 ≥ 85%、拒答类 100% 合规。
  • 报告 tests/report_l3.json 保留每条分数与理由，便于人工抽检；python -m src.report --out report.html

    • 可导出成独立汇报页（评测看板已下线，结果以报告文件为准）。

  • 裁判校准（默认开启，很重要）：植入 3 条错误答案（编造数字 / 答非所问 / 多问只答一半），若裁判不降分，则整轮 L3 判为不可信并门禁失败。实测裁判在三条植入错误上分别得 1 / 1 / 2 分，区分力有效；--calibrate-only 可只补跑校准、复用已有评分省 token。
  • 读数提醒：基础集 26 条曾全部 5.0，说明的是测试集偏简单（问题与知识块近乎一一对应），不代表“质量完美”。所以要另跑难题集（见 5.2）。
  • 立场：L3 结果用于趋势对比，不做逐条绝对判定——裁判本身不确定，把它当“探照灯”而不是“判决书”。

5.2 难题集（13 条，诊断用，不进发布门禁）

基础集测不出「会不会漏、会不会跨文件对齐、会不会编」，所以另做一批题，全部有据可查：

python tests/build_cases_hard.py                                    # 生成难题集
python tests/eval_run.py --cases tests/eval_cases_hard.jsonl --sleep 2 \
       --out tests/report_hard.json                                 # 单独跑难题
python tests/eval_run.py --include-hard                             # 或与基础集一起跑（诊断）
类别条数考什么例
multihop 多跳4需 2+ 知识块组合，漏一处就不完整65 岁以上首次买 R4 要办哪些手续
numeric 数值边界4易错答首次买 R2 需要双录吗（答案：不需要）
conflict 跨文件口径3同一概念在不同文件口径不同双录 6 个月 vs 档案 5 年

作用：这批题一跑就把三个真实缺陷暴露出来了（详见 8. 已知风险）——检索召回不足、引用强制误伤短答案、抽取式兜底不会说“不知道”。 实测：修复前 10/13（76.9%），修掉引用强制与断言问题后 12/13（92.3%），剩余 H10 是检索召回不足导致的真实失败。

召回断言（L1 新增）：expect.retrieval_contains / retrieval_contains_any 检查「该题所需的条款是否被召回」。

{"id": "H10", "expect": {"behavior": "answer",
  "output_contains_any": ["不匹配确认书", "风险不匹配"],
  "retrieval_contains_any": ["风险不匹配", "风险承受能力等级", "第二十九条"]}}

为什么必须有它：L3 裁判只看*检索到的*资料。条款没召回时，模型回「资料中未找到」，对裁判而言反而是忠实的，会给 5 分。也就是说 L3 无法发现检索缺口，这块只能靠确定性的召回断言（或人工）来测。

5.3 异构裁判（换模型判，消自偏好）

同源裁判（用被测模型判自己）会系统性给高分。所以裁判模型可以单独指定：

# 换一个模型家族做裁判，与被测模型不同即可
python tests/eval_l3.py --report tests/report_hard.json \
       --judge-model <另一个模型名> \
       --out tests/report_l3_hard_cross.json
  • --judge-model 指定裁判模型；端点复用 LLM_BASE_URL，要换端点就换环境变量。
  • 建议：裁判尽量选与被测不同的模型家族，否则分数会整体偏高；报告里会记录 judge_channel 与 judge_model。
  • 每次 L3 都会跑裁判校准（植入编造/答偏/答半的错误答案），裁判抓不住就直接判该轮结果不可信。

5.4 召回评测（Recall@k / MRR）

L3 看不见检索缺口（裁判只看检索到的资料），所以召回必须单独测。

python tests/eval_retrieval.py                        # 离线：bm25 / vector / hybrid
python tests/eval_retrieval.py --expand --sleep 1     # 再加查询扩展（需 Key）

实测（11 条带召回标签的难题，top_k=4）：

策略R@1R@4MRR未命中
bm2572.7%90.9%0.883H10
bm25 + 查询扩展81.8%100%0.909—
vector（默认，向量召回 + 重排）72.7%90.9%0.883H10
hybrid72.7%90.9%0.900H10
hybrid + 查询扩展72.7%100%0.864—

结论：

  1. 默认链路是向量召回 + 重排：VectorRerankRetriever 用字符 n-gram 向量做候选召回，再用原问题词覆盖、长片段命中、BM25 和标题命中重排；配置 embedding 后可切到 EmbeddingRetriever（真语义召回）。
  2. 在本语料上，字符 n-gram 向量与 BM25 的 R@1 / R@4 持平（72.7% / 90.9%），差异主要在排序细节。真 embedding 的增益尚未在本语料标注集上实测（没有可用的 embedding 凭据），所以不写「一定更好」。
  3. 查询扩展仍是补齐同义改写的有效手段：H10（「测评 R3 想买 R5」）靠它从漏召回变成第 1 名命中；未配置 Key 时不会启用。
  4. 召回与重排必须分开：扩展词只用于召回，重排只看用户原问题，否则会把原本最相关的块压下去。
样本只有 11 条，单个 query 就是 9pp，结论是方向性的，不是统计显著的。

8. 已知风险与边界

  • 不承诺零幻觉：靠「只依据资料 + 强制引用 + 答不出就明确说明无法找到答案」降低概率、缩小影响面。
  • 离线抽取是兜底，不是正式答案：无 Key 时只做抽取式回填，语义质量有限，上线前务必接真实模型。
  • 知识库 6 份：3 份手写样本 + 3 份 PDF 解析；换成真实制度 PDF 后需重建评测集（用真实 badcase）。
  • PDF 解析边界：只还原文本层——扫描件需 OCR（未含，上传时会被 422 拦下并提示）；加密 PDF 直接拒绝；表格结构与多栏/旋转排版不保证还原，只做行级输出。
  • 合规：金融场景不提供投资建议、不做收益承诺；敏感信息不落日志。
  • 401 invalid api key：Key 失效/复制错误，或 Key 属于第三方中转却仍指向官方端点——需把 LLM_BASE_URL 改成对应中转地址。401 属终止类异常，不重试，直接降级并透传 error。
  • 429 限流：突发调用会触发 429；代码已尊重 Retry-After 并指数退避，批量评测用 --sleep 限速，必要时调大 LLM_MAX_RETRIES。
  • 引用强制：LLM 回答若不含有效 [n]，自动降级为抽取式并标记 degrade_reason=no_citation，杜绝无出处答案。
  • 零宽注入：输入先做零宽/控制字符归一化，避免用零宽字符绕过注入检测；并按合规拒绝「必涨/稳赚/荐股」类请求。
  • L3 裁判偏差：裁判与被测模型同源时存在自偏好，分数系统性偏高；基础集 26 条曾全 5.0，更可能反映“测试集太简单”。缓解手段：校准样本（默认跑）+ 异构裁判（--judge-model 换家族）。
  • 同义改写仍是主要缺口：H10「测评 R3 想买 R5」时，问题措辞（R3/R5）与制度措辞（「超出其风险承受能力等级」）字面重合度低，字符 n-gram 补不上。配置真 embedding（RETRIEVAL=embedding）是正解，但本仓库没有可用的 embedding 凭据，未做同语料增益验证；切换前先跑 tests/eval_retrieval.py。
  • L3 的盲区（重要）：裁判只拿到检索到的 4 块资料。条款没被召回时，「资料中未找到」对裁判来说是忠实且相关的，会给 5 分——所以 H10 这种检索失败，L3 完全看不见（实测同源/异构裁判都给了高分）。结论：L3 评的是「对给定资料的忠实度」，不能替代召回质量评测；召回缺口必须用 retrieval_contains* 断言或人工抽检来测。
  • 引用强制曾误伤短答案（已修）：模型给出正确但未标 [n] 的短答案时，原先直接降级为抽取式，答案反而更差（如「资料未提及收益率」被替换成无关段落）。现改为先补引用（repair_citation，只允许加标注/删无据句），补不上再降级；「资料未提供」类回答天然无出处，予以豁免并标记 citation_exempt_reason。
  • 抽取式兜底不会说“不知道”：降级后只复述最相关段落，无法表达“资料没有”，L3 会判 relevance 1-2 分。这是兜底策略的固有短板，只能靠豁免与更好的降级文案缓解。
  • 裁判侧限流：推理型裁判模型配额更紧，实测 2s 间隔下 9/13 被 429；_judge_call 已尊重 Retry-After 并把退避拉到 5/10/20/30 秒，批量跑建议 --sleep 5。
  • 校准基准要挑对：「多问只答一半」的校准必须用真多问句（按分句判定），否则单问句截断后仍完整，会得出“裁判无区分力”的错误结论。
  • 字符 n-gram 向量不等于语义检索：31 个块、术语密集，它补的是字面重合；默认用 vector 是为了零依赖可跑，不应据此宣称效果提升。真语义检索请配 RETRIEVAL=embedding。
  • embedding 增加一次在线查询延迟与费用：每题一次 /embeddings 调用（已加 128 条查询缓存），超时默认 8s；批量建库按 EMBEDDING_BATCH 计费。索引构建失败/服务不可达时降级词法检索，答案会标 degraded。
  • Redis 是新的单点：限流/幂等/成本依赖它；不可用时回退进程内状态（仍有限流），但多实例之间不再一致。生产建议主从 + 哨兵或托管 Redis，并把 REDIS_TIMEOUT_S 控制在 1~2s。
  • 知识库审批锁是本机文件锁：state.lock 保证同机多进程串行；多实例部署时审批应由单实例处理，或把锁换成 Redis 分布式锁。上传本身不写活动目录，不会出现半写。
  • 索引构建是「分块增量、索引整体替换」：未变更文档复用分块、未变更块复用向量缓存（不重复计费），但检索器对象仍按全量块重建（O(N) 内存与一次扫描），10⁵ 块以上建议换可增量写的索引；重建期间旧索引继续服务，新文档有短暂搜不到窗口。
  • 查询扩展有延迟成本：每题多一次调用（实测 7~25s 波动），且强依赖模型质量；已做「失败静默回退 + 进程内缓存」，但高并发场景需要前置缓存或异步预生成。
  • 上传支持 .md / .txt / .pdf / .docx / .pptx / .xlsx / .csv / .tsv / .html / .eml：全部由服务端解析为 Markdown，上传即入库。.doc / .xls / .msg 老格式需先另存为新格式；扫描 PDF 与图片需先 OCR。
  • DOCX 解析边界：只读正文——文本框、页眉页脚、批注、脚注不提取；图片需 OCR（未含）；文档全是图片时会 422。合并单元格只做文本拼接，不还原跨行跨列。
  • 自动出题的能力边界：heuristic 只能覆盖「有唯一数值」的事实，法规类无数字条款出不了题；llm 模式需要 Key，且模型可能出宽泛问题——关键词已强制校验必须原文出现，但仍建议出题后人工扫一眼。
  • OCR 仍未内置（v1.36.0 明确不做）：零依赖前提下没有可用的 OCR 引擎——Tesseract 要装二进制，

    • PaddleOCR 要装模型与 torch，两者都违背「解压即用」。现在的做法是识别 + 明确报错 + 给出补救步骤 （need_ocr: true），而不是假装能读。这也是与 RAGFlow / QAnything 最实质的差距，短期不打算补。

  • 两万块以上检索超线性：1024 维下每千块从 21 ms 涨到 39 ms（缓存失效 + 内存带宽），

    • docs/BENCHMARK.md 有实测表。到这个规模请装 numpy（自动走 NumpyFlatStore）或改 bm25/hybrid； /api/health 的 warnings 会主动提示。纯 Python 路径没有偷偷优化，只是把拐点说了出来。

  • 目录监听只看文件名/mtime/大小：编辑器若保留时间戳地改内容（少见），不会被发现。

    • 真按内容判断要读全文哈希，那是另一个量级的成本；需要立刻生效就 POST /api/reload。

  • OTel 只导 traces，且是 OTLP/HTTP+JSON：不支持 gRPC、gzip、采样率。要上量请让 collector 做批处理；

    • 导出失败只计数、不影响问答（这是刻意的——观测是旁路）。

  • 页码只对 PDF / PPTX 有（两者都写 <!--page:N--> 标记）：Markdown/DOCX/XLSX 没有可靠页概念，page 为 null，前端不显示「第 N 页」。

    • PPTX 的页码来自 slideN.xml 的 N，与左侧序号通常一致；手工改名后可能不同。

  • 内置 PDF 解析器的覆盖面有限：覆盖经典 xref / xref 流 / 对象流 / Flate / ASCIIHex / ASCII85 / Type0+ToUnicode / 简单字体；遇到无 ToUnicode 的 CID 字体会退化为「赌 CID=Unicode」，此时靠 unmapped_ratio 提示乱码风险，不保证正确。极端文件建议改用 pypdf（.venv）。
