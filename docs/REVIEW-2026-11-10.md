# 五路分区审查汇总（2026-11-10 · v1.32.0）

五个子智能体各自在自己的维度里独立审查，边界按**问题类型**切分而不是按文件切分，
所以同一个文件被多组看过，但每组只报自己那一类。汇总时我做了三件事：
合并重复、消解冲突、并按本项目当前规模重排严重度——子智能体在自己维度内会天然高估
（性能组只看复杂度不知道语料只有 31 块，安全组只看代码不知道默认不对外），
直接采纳会做出错误的优先级。

> **收尾状态（2026-11-10，v1.34.0）**：本文 24 条已全部处理完。
> 1.33.0 修了 17 条（A1–A4、B1、B3–B7、B9、C1、C2、C5–C10），
> 1.34.0 修了剩下 5 条（B2、B8、B10、C3、C4）。两条需要说明取舍：

## 0. 先说一条：上一版文档里的安全判断是错的

`docs/DIFY-AGENT.md` 第 2.1 节我写过：

> 放开监听不等于对局域网开放：`src/security.py` 会校验 Host，只放行回环、
> `ALLOWED_HOSTS` 和 `DOCKER_HOST_NAMES`，其他 Host 一律 403。

**这句话是错的，而且错得危险。** Host 是请求头，攻击者自己填。

证据链：

```python
# src/security.py:64-76
def host_allowed(host_header, extra=None):
    host = _hostname(host_header)
    if host in LOOPBACK_NAMES or host in DOCKER_HOST_NAMES:   # ← 这里
        return True
    ...
```

```python
# src/auth.py:52-54
@property
def enabled(self) -> bool:
    return bool(self.keys)      # API_KEYS 未配置时为 False
```

```python
# src/handlers/base.py:374-377 —— 未启用 Key 时直接放行
if not api_keys.enabled:
    return None, None
```

于是同网段任意机器执行下面这一条就能读完所有笔记：

```bash
curl -H 'Host: host.docker.internal' http://<本机局域网IP>:8000/api/notes
# /api/knowledge、/api/ask、/mcp、/api/settings、/api/storage 同理
```

`--host 0.0.0.0` 是我在上一轮为了让 Dify 连上而推荐的。**推荐本身没错（容器确实需要），
错的是配套的安全说明**：这套组合只在「同一台机器、没有别的设备」的前提下安全，
一旦机器在办公网、咖啡厅 WiFi、云主机上，就是开放的。

这不是「理论风险」：服务没有任何对端 IP 校验（`grep client_address src/security.py` 为空），
唯一拦着的是 Host 头和一个默认关闭的鉴权开关。

### A1 的修法（四个选项，可叠加）

| 方案 | 做法 | 代价 | 建议 |
|---|---|---|---|
| 1. 启动即拒 | `--host` 非回环 且 `API_KEYS` 为空时，启动直接失败并打印提示 | 无 | **必做**，5 行代码 |
| 2. 自动生成 Key | 非回环监听且未配 Key 时，生成随机 Key 写进 `data/` 并打印一次 | 低 | 可选，对 Dify 场景友好 |
| 3. 对端白名单 | 非回环监听时只接受 `TRUSTED_PEERS`（默认 `172.16.0.0/12`，即 Docker 网段） | 需理解网段 | 推荐，配合 1 使用 |
| 4. Host 判据降级 | 明确注释「Host 只防 DNS rebinding，不是访问控制」 | 无 | **必做**，防止下一个人继续误读 |

Dify 场景的推荐组合：`--host 0.0.0.0` + `API_KEYS` 至少一个 + 对端限制在 Docker 网段。
这样 Dify 能连，局域网其它机器不能。

## 5. 同类项目对照：借什么、不借什么

| 同类做法 | 他们怎么做 | 本项目 | 取舍理由 |
|---|---|---|---|
| 混合检索 + Rerank | RAGFlow/FastGPT/Dify 全部标配，视为质量分水岭 | **不引入 rerank 模型**，但借鉴其"候选集内重排"的工程原则 | 零依赖是硬约束，引入 cross-encoder 要么带模型要么调 API，都破坏"单进程可离线跑"。但 C2 那条（重排只看候选）正是这个原则，应该修 |
| 父子切片（Parent-Document Retrieval） | 小块 150 字做向量匹配，命中后拉所属 800 字章节喂模型 | **部分已具备**：`content` 首行是「文档 · 小节」，chunk 带 `chunk_index`；但没有"小块命中→大块喂" | 6 份语料的章节本来就只有几百字，收益不明显。等语料变厚（单章 >2000 字）再做 |
| 引用溯源作为一等公民 | RAGFlow 以"truthful QA + well-founded citations"为立身之本 | **已领先**：服务端生成 `[n]` 并校验 `citation_coverage`，Dify 侧只是渲染不校验 | 这是相对优势，别为了对齐别家而削弱 |
| 知识库版本化 + 审批 | Dify/RAGFlow 基本没有版本审批，改了就生效 | **独有能力**：`versions/vNNNN` + 审批 + 回滚 | A3 修好后这条优势才站得住——现在半成品会锁死上传 |
| RAGAS 四指标（faithfulness / answer relevancy / context precision / context recall） | LLM-as-judge 打分，生产阈值 0.85/0.80/0.75/0.80 | **不引入 LLM-as-judge**，但借用它的**指标分层**思路 | 判官本身要调模型，成本和不确定性都高。可借的是：把现有 36 条用例拆成"检索层"（precision/recall，**不需要模型**，看命中里有没有金标段落）和"生成层"（已有 citation_support_rate） |
| 三层评估（离线金标 → CI 门禁 → 生产采样 5–10%） | 三层缺一层就会在生产才发现问题 | **前两层有**（`eval_run.py` 离线 26/26 + CI 硬门禁），**第三层没有** | 生产采样可低成本实现：从 trace 里按 5% 抽样，只跑"是否有引用 + 引用是否指向存在的段落"这类确定性检查，不用调模型 |
| 慢漂移防护（`--max_drop 0.02`：即使高于绝对线，掉 2 个点也失败） | 防"千次 0.5 分退化" | **没有** | 值得抄，成本极低：给 eval 基线加"相对上次跌幅"判断 |

一句话总结取舍：**别家强在检索侧的模型工程，本项目强在生成侧的可核验性。
跟着别家补模型是拿短板碰人家长板；把引用与版本这两条做扎实，才是这个项目的立足点。**

## 7. 排序口径

`优先级 = 影响(I) × 触发概率(R)`，同分时修复成本(C)低者优先。

- **I**：3 = 数据错误/安全泄露/功能不可用；2 = 性能或正确性劣化；1 = 纯维护成本
- **R**：3 = 默认配置即可触发；2 = 需特定条件（并发、坏值、特定部署）；1 = 理论可达
- **C**：3 = <30 分钟；2 = <1 天；1 = >3 天

| 条目 | I | R | 得分 | C |
|---|---|---|---|---|
| A1 监听暴露 | 3 | 3 | **9** | 2 |
| A2 SSE 无限流 | 3 | 2 | **6** | 1 |
| A3 版本目录半成品 | 3 | 2 | **6** | 2 |
| A4 CI 假绿 | 3 | 2 | **6** | 3 |
| B4 accept 无 503 | 2 | 3 | 6 | 3 |
| B1 status 读全库 | 2 | 3 | 6 | 3 |
| B5 索引投毒 | 3 | 1 | 3 | 3 |
| B9 Redis 假绿 | 3 | 1 | 3 | 3 |

A4 与 B4/B1 同为 6 分，但 A4 成本 30 分钟且是元问题 → 排最前。
A2 成本高于 A3（要改流式生命周期），但影响面覆盖全站 → 排 A3 之前。
